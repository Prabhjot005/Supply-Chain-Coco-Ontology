The Problem

Same Question, Different Answers

Supply chain teams — procurement, planning, and logistics — query the same data but calculate metrics differently. OTD%, fill rate, DOI, and landed cost get computed inconsistently across spreadsheets, BI tools, and ad-hoc SQL.

Before: Fragmented
  • Each team defines OTD% with a different formula
  • Conflicting reports in every standup
  • 30-60 min manual morning report prep per team
  • No governed source of truth
  • Zero automated alerting
After: Governed Ontology
  • 4 canonical metrics locked in a semantic view
  • Same formula resolves identically for everyone
  • Automated daily briefs via email + Slack
  • Agents ACT: create POs, expedite, file Jira
  • Full RBAC + column masking per persona

Target Personas

Procurement Manager

Supplier scorecards, landed cost trends, reorder decisions, PO creation with cost justification.

Planning Analyst

Inventory health, demand forecasts (ML), fulfillment risk scoring, stock gap analysis.

Logistics Coordinator

Shipment tracking, delay detection, carrier OTD%, expedite management with Jira + Slack alerts.

Pipeline Details

4 INCREMENTAL Dynamic Tables

Delivery perf, inventory position, landed cost, order fulfillment. 1-hour target lag. Automatic refresh.

DT + View Split (Design Decision)

CURRENT_DATE() blocks INCREMENTAL refresh. DT stores raw data; V_ORDER_FULFILLMENT computes 4-factor risk scores (0-12) at query time.

3 CDC Streams + 3 Tasks

Event-driven alerts: shipment delays, low inventory, order risk. Tasks poll every 5 min via SYSTEM$STREAM_HAS_DATA.

ML FORECAST Model

Multi-series demand forecasting. 30-day projections with confidence intervals. Staleness checks built into the demand_planner skill.

Clean separation: SPs handle guardrails + DB writes. Agents orchestrate MCP calls (Jira, Slack, Gmail). SPs cannot call MCP, so the agent is the workflow conductor. If Slack fails, the DB write and Jira ticket still succeed — graceful degradation.

Reusable Skills — 5 Domain-Specific Instruction Sets

Skills are declarative instruction sets (Markdown files) that give each agent a repeatable, multi-step playbook for a specific domain task. The agent loads the skill, follows its steps in order, and applies its guardrails — no ad-hoc prompting required.

SkillUsed ByCore MechanismKey Guardrails
supplier_scorecard Procurement Agent Calls GENERATE_SCORECARD UDF to compute a composite 0-10 score (OTD 40%, Quality 30%, Cost 30%). Ranks suppliers, flags underperformers (score < 6.0 or OTD < 80%), and drives rating changes via UPDATE_SUPPLIER_RATING SP + Slack alert. Low-confidence warning if < 5 shipments; max 1-tier rating change per update; cost-vs-quality always shown together.
cost_analyzer Procurement Agent Queries DT_LANDED_COST to break unit cost into material + freight + duty components. Builds a cost-quality matrix by cross-referencing each supplier's scorecard and OTD%. Runs trend analysis (current month vs prior 3 months) to identify which component drives increases, then computes annual savings opportunities across alternative suppliers. Never recommends on cost alone; flags misleading savings where freight negates material discount; small-sample and stale-data warnings; currency consistency check.
demand_planner Planning Agent Runs inference on a pre-trained Snowflake ML FORECAST model (multi-series, no retraining per query). Returns 30-day projections with confidence intervals, trend direction (rising/falling/stable at ±10% threshold), and seasonality detection. Checks training-data outliers (single day > 5× median) and model staleness (> 7 days). Falls back to 30-day rolling average if < 60 days of history; always shows confidence range, not just point estimate; flags zero-demand parts as possibly discontinued.
reorder_advisor Procurement + Planning Agents Identifies parts below reorder point from DT_INVENTORY_POSITION, delegates demand forecasting to demand_planner, scores candidate suppliers via GENERATE_SCORECARD, then calculates reorder quantity: (projected_30d_demand + safety_stock) − on_hand. Presents an editable recommendation — user can adjust quantity or supplier before confirming. Executes via CREATE_PURCHASE_ORDER SP + Slack notification. 3× quantity sanity check; $50K budget cap per PO; 7-day duplicate PO detection; passes through demand_planner confidence level; graceful fallback if no demand data.
shipment_tracker Logistics Agent Queries in-transit shipments and historical carrier performance to compute a revised ETA (expected + avg carrier delay). Classifies each shipment into 4 risk tiers: ON_TRACK → AT_RISK → DELAYED → CRITICAL (cross-referenced with order risk from DT_ORDER_FULFILLMENT). For CRITICAL shipments, drives the full expedite workflow: TRIGGER_EXPEDITE SP → Jira ticket → UPDATE_ALERT_JIRA → Slack alert. ETA confidence rated by carrier history volume (HIGH/MEDIUM/LOW); 48h duplicate expedite block; max 3 escalations per shipment; hands off to reorder_advisor if root cause is low stock, not late shipment.
Design pattern: Skills are composable — reorder_advisor delegates to demand_planner, and shipment_tracker hands off to reorder_advisor. Each skill owns its guardrails independently, so safety rules apply regardless of which agent or workflow invokes them. Skills are shared across agents: reorder_advisor is used by both Procurement and Planning agents with identical logic.

Guardrails — Defense in Depth

Input Validation

Every SP validates types, checks record existence, rejects invalid parameters before any DB mutation.

Business Rules

48h duplicate expedite. Max 3 escalations. Max 1-tier rating change. $50K PO budget cap. 3x quantity sanity.

User Confirmation

All write operations require explicit confirmation. Agent presents proposal with full details first.

Structured Errors

SUCCESS: / ERROR: / GUARDRAIL_DUPLICATE: / GUARDRAIL_ESCALATION: — agent parses prefix and responds.

Data Staleness

If data is stale or insufficient, agent discloses the limitation. Never fabricates an answer.

Graceful Degradation

60s timeout, 32K token cap. tool_not_accessible: accept. Slack failure doesn't block the critical path.
